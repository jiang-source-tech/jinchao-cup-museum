## Problem Statement

`/xiaoxin/control/` 在产品语义上是管理员控制台，但当前认证和记忆接口仍沿用普通用户自助页的 owner 隔离模型。管理员使用本地控制台账号登录后，记忆主体列表只返回当前账号名下的主体，详情接口也要求目标主体属于当前登录账号。

这会产生三个直接问题：

1. 管理员无法查看小程序用户、真实绑定设备和已确认声纹产生的记忆。
2. 控制台账号、微信用户账号、设备归属和声纹主体分离时，页面会把账号隔离误报成“记忆链路未建立”。
3. 页面无法区分“没有记忆”“说话人未确认”“设备未绑定”“管理员无权访问”和“后台投影故障”。

线上数据已经证明该问题不是假设：

- 控制台本地账号是 `jiang`。
- 当前活跃设备是 `1c:db:d4:48:d1:50`。
- 该设备绑定到微信小程序用户“小明”，不属于 `jiang`。
- 已确认声纹及其 `user_speaker` 主体属于“小明”。
- 当前管理员记忆接口按 `jiang` 过滤，因此看不到真正包含陪伴记忆的已确认主体。
- 已确认主体的后台投影实际存在关系时期和 13 条 Evidence，数据本身并未丢失。

当前行为的根因是授权模型错误，不应通过修改数据归属、把小程序用户迁移到管理员账号、降低声纹阈值或取消所有 owner 校验来规避。

## Goals

1. 将控制台管理员权限建模为明确、可测试、可审计的授权能力。
2. 允许管理员跨用户查看设备、说话人、记忆主体和安全记忆投影。
3. 保留普通用户和小程序会话的 owner 隔离。
4. 让页面准确解释主体为什么可用或不可用。
5. 默认选中最值得诊断的活跃、已确认主体，而不是按创建时间碰运气。
6. 管理员控制操作必须作用于目标主体的真实 owner 上下文，并记录操作者与目标所有者。
7. 整个迁移可回滚，不修改现有记忆归属，不丢失 Evidence。

## Non-Goals

1. 不把控制台账号与微信用户账号合并成同一身份。
2. 不修改声纹识别模型、阈值或注册流程。
3. 不重写陪伴记忆 V2 的 Evidence、Epoch、Projection 和 Reflection 规则。
4. 不允许管理员跨 owner 合并记忆主体。
5. 不把原始对话全文、敏感 payload 或未脱敏查询文本暴露到控制台。
6. 不以“请求带 Cookie”作为管理员判断条件。
7. 不在本计划评审通过前执行生产数据库迁移。

## Current-State Diagnosis

### Authentication and authorization are conflated

当前系统能识别 Cookie 会话、Bearer 会话和设备凭证，但用户模型没有明确的管理员角色。一部分设备控制逻辑把 Cookie 会话当作控制台会话，另一部分记忆逻辑仍按当前用户过滤。

结果是同一控制台页面中的不同功能拥有不同的权限边界。凭证传输方式事实上承担了部分授权职责，这既不完整，也不可审计。

### Memory APIs are owner-scoped

现有主体列表、主体详情、主体合并和记忆控制接口以当前登录用户作为 owner。该模型对用户自助页面是正确的，对管理员页面则错误。

尤其是详情投影使用“当前登录用户”的陪伴实体和学生资料构造上下文，而管理员查看其他用户时，必须使用“目标主体 owner”的陪伴实体和资料。否则即便放宽列表权限，投影仍会串错上下文。

### The projection is not an admin diagnosis model

陪伴投影对未确认说话人采用 fail-closed 策略，只返回中性 policy，不返回私人 Evidence、陪伴实体或记忆主体标识。这是正确的运行时安全行为。

但控制台直接用投影 payload 是否包含 `pet_id` 和 `memory_subject_id` 判断链路健康，导致“安全隐藏字段”被解释成“身份链断裂”。管理员诊断需要独立的只读模型，不能从面向语音或小程序的安全投影反推后台身份状态。

### The default selection is misleading

当前主体按创建时间倒序返回，页面选择第一条。旧设备的 `device_unknown` 主体可能比当前活跃设备的已确认主体更早进入管理员视野，导致首页显示空状态，而真正有记忆的主体藏在另一个账号作用域中。

## Solution Overview

采用“身份角色、管理员 API、管理员读模型、操作审计”四层方案。

### 1. Explicit administrator role

用户身份增加明确角色，至少区分：

- `admin`：可以访问管理员控制台和管理员 API。
- `user`：只能访问自己的用户数据和小程序 API。

管理员判断只读取服务端身份角色，不依赖 Cookie、Bearer、用户名格式、来源 IP 或页面路径。

Cookie 和 Bearer 继续作为认证凭证的不同载体；同一个非管理员用户无论用哪一种载体，都不能调用管理员 API。

### 2. Separate administrator API namespace

新增独立管理员命名空间，不改变现有 owner-scoped API 的语义。

管理员接口按用途分为：

- 全局设备与说话人概览。
- 全局记忆主体列表。
- 单主体管理员记忆详情。
- 明确的管理员记忆控制。
- 管理员主体合并，但只允许同 owner 内合并。
- 管理员访问和控制审计查询。

现有用户接口继续按当前用户过滤。这样小程序、未来用户自助页和现有调用方不会因管理员需求而扩大权限。

### 3. Dedicated administrator memory read model

管理员主体列表不能只返回 `MemorySubject`。它需要一个组合后的只读模型，至少包含：

- 主体标识、类型、显示名、创建时间和合并状态。
- owner 标识、显示名、账号来源和账号状态。
- 设备标识、显示名、绑定状态、当前 owner、最后在线时间和连接状态。
- 说话人标识、声纹键的安全摘要、确认状态和最后识别时间。
- 陪伴实体标识、状态和陪伴开始时间。
- 当前关系时期标识和状态。
- Evidence、候选事实、后台任务和错误状态的安全计数。
- 可持久化状态及结构化阻断原因。

建议使用结构化状态码而不是前端猜测：

- `ready`
- `speaker_unconfirmed`
- `device_unbound`
- `owner_missing`
- `pet_missing`
- `pet_pending`
- `subject_merged`
- `projection_unavailable`

页面文案由状态码确定，不再通过 payload 缺少字段推断。

### 4. Target-owner projection context

管理员查看主体详情时分离两个身份：

- Actor：当前管理员，用于授权和审计。
- Subject owner：目标记忆主体的真实 owner，用于获取个人小芯、学生资料、关系时期和 Evidence。

管理员身份不能替代目标 owner 进入陪伴投影。所有记忆读取和控制都必须使用目标主体的 owner 上下文。

### 5. Safe global subject selection

管理员主体列表支持搜索、owner 过滤、设备过滤、主体类型过滤和阻断状态过滤。

默认排序建议依次考虑：

1. 未合并主体优先。
2. 当前在线或最近在线设备优先。
3. 已绑定设备优先。
4. `user_speaker` 已确认主体优先。
5. 活跃陪伴实体优先。
6. 最近交互时间优先。

默认选中项必须由后端返回的稳定排序或显式推荐标识决定，避免前端重复实现业务排序。

### 6. Admin audit log

管理员读取私人记忆详情和执行控制命令必须记录：

- 操作者用户标识。
- 目标 owner 标识。
- 目标主体标识。
- 操作类型。
- 请求时间、结果状态和失败码。
- 控制命令的幂等键。
- 安全原因摘要，不记录原始私人文本。

读取列表可按请求级记录；读取具体详情和执行控制必须逐次记录。

## Registration and Migration Decisions

### New installations

首次启动只允许创建第一个本地控制台管理员。管理员创建成功后，公开注册入口关闭。后续管理员账号必须由已有管理员创建或通过受控运维命令提升。

小程序会话创建的账号始终是 `user`，不得因为是数据库中的第一个用户而成为管理员。

### Existing installations

迁移新增角色字段时，所有现有账号默认 `user`，不根据 Cookie、用户名或 `mp:` 前缀自动授予管理员。

生产环境执行一次明确的管理员提升操作，将现有 `jiang` 本地账号提升为 `admin`。提升前必须备份身份数据库；提升后验证只有预期账号拥有管理员角色。

迁移失败时服务应 fail closed：用户接口继续可用，管理员 API 返回明确不可用状态，不能回退成“所有 Cookie 都是管理员”。

## API Contract Decisions

1. 用户主体接口保持 owner-scoped，不改变返回范围。
2. 管理员主体列表使用独立命名空间和独立 DTO。
3. 管理员详情返回 `identity`、`readiness`、`projection`、`diagnostics` 和 `audit` 五个清晰区域。
4. 未确认说话人可以返回管理员身份诊断，但私人 Evidence 必须为空。
5. 已确认说话人使用目标 owner 构造投影，并返回安全 Evidence。
6. 合并接口要求 source 和 target 属于同一 owner；跨 owner 固定拒绝。
7. 已合并旧主体默认不出现在可操作列表，可通过诊断过滤器查看。
8. 所有管理员写操作要求 CSRF 防护、幂等键和服务端权限复核。
9. 错误使用稳定错误码，页面不解析英文 message 决定状态。

## UI Decisions

### Subject list

每个主体条目优先展示：

- owner 显示名和账号来源。
- 设备名、MAC、绑定状态和最后在线时间。
- 说话人名称和确认状态。
- 记忆可用状态。
- 已确认事实、候选事实和 Evidence 计数。

内部 ID 作为次要诊断信息，不作为第一视觉信号。

### Memory detail

详情首屏依次展示：

1. 当前查看的用户、设备和说话人。
2. 记忆是否可用，以及不可用的具体原因。
3. 用户画像和最近形成的安全事实。
4. 关系阶段和最近记忆更新时间。
5. 默认折叠的高级诊断。

### Blocked subjects

- `speaker_unconfirmed`：说明未知说话人禁止形成私人长期记忆。
- `device_unbound`：说明设备没有用户 owner。
- `owner_missing`：说明历史主体没有有效账号归属。
- `pet_pending`：说明个人小芯尚未激活，而不是声称数据库故障。
- `projection_unavailable`：明确标为服务异常，并提供重试和日志关联标识。

## Testing Decisions

测试只断言外部行为和权限边界，不绑定内部 SQL 或函数实现。

### Schema and authentication

- 新数据库首次管理员创建。
- 小程序账号永远是普通用户。
- 现有数据库角色迁移。
- 无管理员时 fail closed。
- 普通用户不能访问管理员 API。

### Memory list

- 管理员能看到多个 owner 的主体。
- 普通用户只能看到自己的主体。
- 列表包含安全 owner、设备、说话人、陪伴实体和 readiness 信息。
- 默认排序把当前在线的已确认主体放在旧未知主体之前。

### Memory detail

- 管理员可读取其他 owner 的已确认主体安全投影。
- 投影使用目标 owner 的 pet 和 profile，不使用管理员自己的数据。
- 普通用户读取他人主体返回 404 或统一权限错误，不泄露主体存在性。
- 未确认主体不返回私人 Evidence。
- 已合并主体不可操作。

### Memory control

- 管理员可对目标 owner 的已确认主体执行允许的控制。
- 非管理员固定拒绝。
- 跨 owner 合并固定拒绝。
- 幂等冲突、确认短语和审计记录均可验证。

### Browser acceptance

- 桌面和手机尺寸无溢出、遮挡或跳动。
- 管理员登录后默认展示当前设备的已确认主体。
- owner、设备和说话人信息可清楚区分。
- 高级诊断默认折叠并可展开。
- 控制台无 JavaScript 错误，接口无未处理 4xx/5xx。

### Production smoke test

- 管理员能看到当前设备 `1c:db:d4:48:d1:50`。
- 能定位到“小明”的 `user_speaker` 主体。
- 详情中的 pet、subject 和 relationship epoch 与数据库一致。
- 安全 Evidence 计数与后台诊断一致。
- `jiang` 自身的旧 `device_unknown` 主体仍存在，但不会成为默认项。
- 小程序用户访问范围不扩大。

## Rollout and Rollback

### Rollout

1. 备份身份数据库和陪伴记忆数据库。
2. 部署仅包含角色 schema 和迁移工具的版本。
3. 明确提升 `jiang` 为管理员并核对角色表。
4. 部署管理员只读列表和详情 API。
5. 使用接口测试验证跨用户只读和普通用户隔离。
6. 切换控制台前端到管理员 API。
7. 最后启用管理员控制命令和审计。
8. 完成真实设备与手机浏览器验收后再清理兼容代码。

### Rollback

1. 前端可先回退到旧 owner-scoped API。
2. 管理员 API 可关闭而不影响用户 API。
3. 角色字段保留不会影响旧版本读取；不得删除或重写用户、主体和 Evidence。
4. 数据库回滚只恢复 schema 前备份，不执行反向主体迁移。
5. 审计表可以保留，不能随应用回滚删除。

## Commits

每个提交必须独立通过测试并保持服务可启动。

1. **记录权限矩阵和失败用例**
   - 增加管理员与普通用户的黑盒权限测试。
   - 测试先展示当前缺陷，不修改生产行为。

2. **增加用户角色 schema**
   - 增加角色字段和约束。
   - 更新用户模型序列化与数据库迁移测试。
   - 所有旧账号默认普通用户。

3. **增加管理员运维提升能力**
   - 提供显式、可重复执行的管理员提升命令。
   - 输出变更前后角色并拒绝不存在账号。
   - 不在业务代码中硬编码 `jiang`。

4. **关闭不受控的管理员注册**
   - 新安装允许创建首个管理员。
   - 已有管理员后关闭公开控制台注册。
   - 小程序账号固定创建为普通用户。

5. **引入统一管理员授权守卫**
   - 管理员 API 只依赖服务端角色。
   - 删除“Cookie 等于管理员”的隐式判断。
   - 补齐 401、403 和不泄露资源存在性的测试。

6. **建立管理员记忆查询服务**
   - 一次性组合 owner、设备、说话人、pet、subject 和健康状态。
   - 避免页面发起 N+1 请求。
   - 只返回安全摘要和计数。

7. **增加管理员主体列表 API**
   - 支持分页、搜索和过滤。
   - 后端给出稳定默认排序和 readiness 状态码。
   - 保持用户主体接口不变。

8. **增加管理员记忆详情 API**
   - 分离 actor 与 target owner。
   - 使用目标 owner 构造陪伴投影。
   - 未确认主体只返回中性诊断。

9. **增加管理员读取审计**
   - 记录详情查看行为和结果状态。
   - 不记录原始私人文本。

10. **切换控制台主体列表**
    - 展示 owner、设备、说话人和 readiness。
    - 加入搜索、过滤和清晰空状态。
    - 默认选择后端推荐主体。

11. **切换控制台记忆详情**
    - 使用结构化 readiness，而不是检查 payload 缺失字段。
    - 保留用户画像优先和高级诊断折叠设计。

12. **增加管理员控制与写审计**
    - 管理员控制使用目标 owner 上下文。
    - 增加 CSRF、幂等和同 owner 合并限制。
    - 每次写操作记录 actor 与 target。

13. **完成端到端和生产验收**
    - 运行权限、身份、陪伴记忆和静态控制台套件。
    - 完成桌面、手机和真实设备 smoke test。
    - 记录部署、回滚和已知限制。

## Acceptance Criteria

1. `jiang` 管理员能在控制台看到“小明”的已确认主体及其安全记忆内容。
2. 小程序普通用户仍不能读取其他 owner 的任何主体或记忆。
3. 控制台不再依赖当前管理员自己的 pet 构造目标用户投影。
4. 未确认主体显示准确阻断原因，不误报数据库故障。
5. 当前在线的已确认主体默认优先展示。
6. 管理员读取和控制都有可查询审计记录。
7. 跨 owner 合并始终被服务端拒绝。
8. 回滚管理员功能不会修改或丢失现有主体、Epoch 和 Evidence。

## Open Questions for Review

1. 管理员控制台是否只允许一个超级管理员，还是需要多个管理员账号？
2. 管理员读取私人记忆详情是否需要填写查看原因？
3. 管理员列表是否默认隐藏未绑定设备和已合并主体？
4. 高风险控制是否需要二次认证，而不仅是确认短语？
5. 审计记录需要保留多久，是否需要导出？
6. 第一阶段是否只开放只读诊断，待稳定后再开放写控制？

## Recommended Review Decision

建议先批准“显式角色 + 独立管理员只读 API + 管理员读模型 + 审计”四项，第一阶段只上线跨用户只读能力。管理员写控制、主体合并和高风险操作作为第二阶段，在只读权限和审计稳定后再启用。

不建议批准以下方案：

- 仅按 Cookie 判断管理员。
- 直接让现有用户接口在控制台会话下返回全库数据。
- 把设备和小程序用户迁移到 `jiang` 名下。
- 前端自行拼接多张表并猜测 readiness。
- 为了让页面有内容而向未知说话人开放私人记忆。
