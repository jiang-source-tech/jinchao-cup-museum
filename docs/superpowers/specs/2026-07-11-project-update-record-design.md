# 项目更新记录体系设计

日期：2026-07-11
时区：Asia/Shanghai（UTC+8）
状态：已获方案批准，等待规格确认

## 1. 目标

建立一套供开发、测试和运维共同使用的项目更新记录体系。它必须让读者能够回答以下问题：

- 为什么进行这次更新；
- 修改前存在什么问题；
- 实际修改了哪些服务、固件、协议、配置、数据或文档；
- 修改前后的行为有什么差异；
- 更新会影响哪些用户和运行环境；
- 如何部署、验证、观察和回滚；
- 哪些结论已经验证，哪些仍待实机或生产环境验证。

该体系记录整个项目今后的正式更新，不局限于通知 TTS。

## 2. 采用方案

采用“总索引 + 通用模板 + 每次更新独立详情”的两层结构：

```text
docs/updates/
├── README.md
├── UPDATE_TEMPLATE.md
└── 2026/
    └── 2026-07-11-notification-tts-reliable-playback.md
```

不采用无限增长的单文件日志，因为它会混合开发细节、部署说明和历史验证结果，长期难以检索。不按开发、测试、运维拆成三份日志，因为同一次更新会被重复记录并产生内容漂移。

## 3. 总索引设计

`docs/updates/README.md` 是更新记录的统一入口，包含：

1. 文档用途和适用范围；
2. 时间、状态和排序规则；
3. 如何新增一条正式更新；
4. 按时间倒序排列的更新索引表；
5. 更新状态、类型和范围的统一词汇。

索引表字段固定为：

| 字段 | 含义 |
|---|---|
| 更新时间 | 更新完成或发布到 `main` 的北京时间 |
| 更新编号 | `UPD-YYYYMMDD-NNN` 格式的稳定编号 |
| 更新主题 | 能直接表达用户或系统变化的标题 |
| 更新类型 | 功能、缺陷修复、可靠性、性能、安全、配置、文档或基础设施 |
| 涉及范围 | 服务端、固件、协议、配置、数据、部署或文档 |
| 状态 | 设计中、开发中、待验证、已发布、已回滚或已废弃 |
| 详情 | 指向独立更新详情文件的相对链接 |

最新记录放在表格最上方。同一天存在多次更新时，编号尾号按 `001`、`002` 递增。

## 4. 时间与状态规则

- 所有时间统一使用北京时间，并明确标注 `UTC+8`。
- 已知精确时间时记录到分钟，例如 `2026-07-11 07:45（UTC+8）`。
- 无可靠证据时不得编造具体时间，必须写“具体时间未记录”。
- 只有已经合并并推送到目标分支的更新才能标记为“已发布”。
- 自动化测试、构建验证、实机验收和生产验证必须分别记录，不能互相替代。
- 未完成实机验收时，必须明确标记为“实机验收未执行”或“实机验收受阻”。

## 5. 通用模板设计

`docs/updates/UPDATE_TEMPLATE.md` 包含以下固定章节：

1. 更新信息；
2. 更新摘要；
3. 更新背景；
4. 修改目标与非目标；
5. 修改前后对比；
6. 系统流程变化；
7. 详细修改内容；
8. 协议、配置与数据变化；
9. 影响范围与兼容性；
10. 部署与迁移说明；
11. 验证结果；
12. 风险与已知限制；
13. 回滚方案；
14. 运行观察项；
15. 后续事项；
16. 关联提交与文档；
17. 文档修订记录。

模板中的提示文字必须明确告诉记录者需要提供什么证据。模板可以使用待填写标记，但正式更新详情不得保留未解释的占位符；无法获得的信息必须明确写出未知原因。

## 6. 独立更新详情设计

每次正式更新使用一个 Markdown 文件，路径规则为：

```text
docs/updates/YYYY/YYYY-MM-DD-<英文短名称>.md
```

文件名日期采用发布或合并到目标分支的日期。英文短名称使用小写连字符，不使用不稳定的内部任务编号。

详情页同时服务三类读者：

- 开发人员关注原因、模块、接口、提交和技术行为；
- 测试人员关注前后对比、验收场景、自动化证据和未验证项；
- 运维人员关注部署顺序、配置、可观察指标、风险和回滚。

详情页不复制完整代码 diff，而是记录行为变化、关键文件或模块、协议字段、配置项和稳定提交链接。

## 7. 第一条更新记录

首条正式记录为：

```text
UPD-20260711-001：通知 TTS 可靠播放与屏保唤醒
```

它至少记录：

- 屏保或省电状态下通知 TTS 可能断续、首段丢失的原始现象；
- “屏幕刷新造成 CPU 不足”属于待实机验证的推断，而不是已证明根因；
- MQTT 负责通知和唤醒，WebSocket/TCP 负责 TTS start/stop、二进制音频和 ACK；
- `tts:start → ready → 音频 → done/error` 的新流程；
- pre-roll、完整重试、attempt lease、sentence/generation/epoch 隔离；
- 固件退出屏保、return state、I2S 有限写入和 `output_write_timeout`；
- 服务端与固件的兼容边界和 legacy 路径；
- 服务端 merge commit `5a99cd0aeb97fed2233717276d4f2d906f37742c`；
- 固件 merge commit `1b483480717bf333f4bef176e911d761834503d7`；
- 服务端测试 `487 passed, 1 skipped`；
- 固件 Python 测试 `264 passed`；
- 9 个相关 host tests 通过；
- Waveshare 1.46 ESP-IDF v5.5.4 fullclean 构建通过，`ai_pet.bin` 为 5,673,808 字节，应用分区剩余 55%；
- 因没有串口/USB 设备，实机物理端到端验收仍未执行；
- 推荐部署顺序、运行观察字段和回滚目标。

不得把软件自动化验证写成物理播放已经通过。

## 8. 维护流程

今后每次正式更新按以下顺序记录：

1. 从 `UPDATE_TEMPLATE.md` 复制生成详情文件；
2. 填写背景、行为变化、影响、部署、验证和回滚；
3. 核对时间、提交哈希、测试数字、配置值和链接；
4. 明确区分已验证事实、推断和未知项；
5. 在 `README.md` 顶部追加索引记录；
6. 与代码更新一起评审，或在发布后立即补充；
7. 后续补做实机或生产验证时，更新验证章节和文档修订记录，不篡改原始发布时间。

## 9. 验收标准

本设计实施完成后必须满足：

- `docs/updates/README.md`、`UPDATE_TEMPLATE.md` 和第一条 TTS 更新详情均存在；
- 总索引能够直接定位第一条更新详情；
- 模板覆盖开发、测试和运维所需信息；
- 第一条详情中的时间、提交和测试证据可核对；
- 第一条详情明确标出实机验收尚未执行；
- 文档相对链接有效；
- Markdown 无未解释的 `TBD`、`TODO` 或虚构数据；
- 不修改 `docs/README.md` 和 `docs/operations/xiaoxin-real-device-acceptance-ledger.md`。

## 10. 范围边界

本次只建立更新记录文档体系并记录已经完成的通知 TTS 更新，不实现自动生成日志、Git hook、CI 发布机器人、网页管理界面或数据库存储。未来确有维护成本后再评估自动化。
