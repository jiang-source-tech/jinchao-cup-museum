# 小芯服务端工程审计清单

审计日期：2026-07-21

审计范围：仓库结构、Python 运行时、Java 管理 API、Web/移动端、Docker、GitHub Actions、测试与项目文档

审计基准：以可维护、可复现、可安全部署的生产级工程为标准

结论置信度：代码库与配置问题高；真实生产稳定性中

## 1. 总体结论

当前项目已经具备真实产品闭环，不是演示性质的 AI 套壳项目。语音链路、设备投递、MQTT、ACK、离线处理、身份隔离和陪伴记忆均有实际实现，Python 核心能力也有较强的专项测试。

主要问题不在“功能太少”，而在工程治理没有跟上功能增长速度：CI 没有质量门禁，Java 和前端测试薄弱，部署默认安全配置不合格，测试环境不能从仓库完整复现，少数核心文件已经过度膨胀，真实设备验收仍有未闭合项目。

当前综合工程评分：`68/100`。

## 2. 优先级定义

| 优先级 | 含义 |
| --- | --- |
| P0 | 已经构成凭据泄露或生产安全风险，应立即处理 |
| P1 | 会直接破坏交付可信度、部署安全性或回归可靠性，应在继续扩展功能前处理 |
| P2 | 已形成明显维护成本和架构债务，应纳入近期重构计划 |
| P3 | 暂不阻塞当前运行，但会持续增加升级、协作或排障成本 |

## 3. P0：立即处理

### SEC-01：受 Git 跟踪的配置包含疑似真实高德 API Key

- **确认事实**：`main/xiaozhi-server/config.yaml:74` 包含非占位符形式的 `amap_api_key`，该值从历史提交 `0f2d2c7` 起进入 Git 历史。
- **未确认事项**：本次审计没有调用高德接口验证该 Key 当前是否有效。
- **影响**：即使 Key 已失效，它仍展示了把真实凭据写入默认配置的流程缺陷；若有效，可能被滥用并消耗额度。
- **处理方向**：立即在供应商侧轮换或注销；默认配置只保留空值；运行时从环境变量或密钥管理系统读取；CI 增加 secret scanning。
- **验收标准**：当前配置和新提交均不含真实 Key；旧 Key 已在供应商侧失效；自动扫描能阻止同类提交。

### SEC-02：全量 Docker 部署使用固定数据库密码和空 Redis 密码

- **确认事实**：`main/xiaozhi-server/docker-compose_all.yml:54-57` 使用 MySQL 用户 `root`、密码 `123456`，Redis 密码为空；`80` 行再次固定 `MYSQL_ROOT_PASSWORD=123456`。
- **影响**：容器网络内任一服务被攻破后，数据库和 Redis 几乎没有第二层保护；复制默认部署会形成大量相同凭据实例。
- **处理方向**：密码改为必填环境变量，缺失时启动失败；应用使用最小权限数据库账号；Redis 启用认证；生产部署使用独立 `.env` 或 secrets 文件且不入库。
- **验收标准**：仓库不存在可工作的默认密码；未提供强凭据时 Compose 明确失败；应用账号不能执行数据库管理操作。

## 4. P1：交付与可靠性阻塞项

### CI-01：GitHub Actions 没有测试质量门禁

- **确认事实**：`.github/workflows/` 只有基础镜像和发布镜像工作流，未执行 Python 测试、Java 测试、前端 lint/type-check、覆盖率、依赖审计或镜像扫描。
- **影响**：代码可以在所有自动测试未运行的情况下进入 `main` 并发布镜像；“本地测试通过”不能替代持续集成。
- **处理方向**：增加独立 CI 工作流，并把 Python、Java、Web、移动端检查设置为合并必需状态。
- **验收标准**：任一模块测试或静态检查失败时，PR 不能合并，发布任务不能执行。

### CI-02：Java 测试被 Maven 配置和镜像构建双重关闭

- **确认事实**：`main/manager-api/pom.xml:278` 配置 `<skipTests>true</skipTests>`；`Dockerfile-web:14` 使用 `mvn clean package -Dmaven.test.skip=true`。
- **影响**：已有 Java 测试默认不会运行，管理 API 的认证、设备、数据库迁移等回归无法被发布流程发现。
- **处理方向**：移除 POM 中的全局跳过；CI 显式执行 `mvn test`；镜像构建只消费已经通过测试的构件或至少不再强制跳过。
- **验收标准**：故意破坏一个 Java 测试时，CI 和发布流程均失败。

### TEST-01：Python 测试环境不能完全从仓库复现

- **确认事实**：`main/xiaozhi-server/requirements.txt` 没有 `pytest`、`pytest-asyncio` 等测试依赖；仓库也没有 `requirements-dev.txt`、`pyproject.toml`、`pytest.ini` 或 `tox.ini`。
- **本次验证**：核心记忆、并发、策略、召回和运行时集成子集使用独立 `--basetemp` 得到 `142 passed in 10.73s`；`compileall` 通过。完整测试首次收集因本机未安装运行依赖而终止，并出现未知 `pytest.mark.asyncio` 警告。
- **边界说明**：本机未安装运行依赖本身不算仓库缺陷；仓库没有声明测试工具和异步测试插件才是可复现性缺陷。
- **处理方向**：建立独立开发依赖锁定文件和 pytest 配置；在全新 Python 3.10 环境中执行安装与全量测试。
- **验收标准**：只按照仓库文档操作即可在干净环境中运行全部测试，且无 unknown mark、意外 skip 或依赖缺失。

### TEST-02：测试覆盖在各模块之间严重失衡

- **确认事实**：Python Xiaoxin 目录有大量专项测试；Java 只有少量测试且默认跳过；Web 管理端没有测试脚本；移动端有 lint/type-check，但没有发现自动测试门禁。
- **影响**：核心 Python 模块的质量不能替 Java、Web 和移动端背书，跨模块协议变化尤其容易漏检。
- **处理方向**：优先补认证、设备绑定、配置读取、OTA/WebSocket 合同、控制台关键操作和前端主要流程的契约/集成测试。
- **验收标准**：每个可部署模块至少具备构建、静态检查、单元测试和一条关键流程集成测试。

### FE-01：Web 管理端缺少基本工程检查和确定性安装

- **确认事实**：`main/manager-web/package.json` 只有 `serve`、`build` 和 `analyze`，没有 `lint`、`test` 或 `type-check`；仓库未跟踪该模块的 lockfile；依赖中存在可疑的 `"xiaozhi": "file:"`。
- **影响**：依赖解析可能随时间变化，前端错误主要依赖人工发现，Docker 中的 `npm install` 无法保证可重复构建。
- **处理方向**：修正自引用依赖；生成并提交 lockfile；Docker 使用 `npm ci`；增加 ESLint、类型检查和关键页面测试。
- **验收标准**：相同提交在干净环境中得到相同依赖树；错误代码会被 CI 阻止。

### BUILD-01：基础镜像构建产物与服务端 Dockerfile 使用的镜像不一致

- **确认事实**：基础镜像工作流推送 `ghcr.io/${repository}:server-base`，但 `Dockerfile-server:2` 仍基于 `ghcr.nju.edu.cn/xinnan-tech/xiaozhi-esp32-server:server-base`。
- **影响**：当前仓库构建出的基础镜像可能根本没有被服务端镜像消费；构建结果依赖上游镜像和第三方镜像代理，存在漂移与供应链风险。
- **处理方向**：统一镜像来源；通过明确的 build arg 或固定 digest 使用本仓库产物；记录基础镜像 SBOM。
- **验收标准**：基础镜像更新后，服务端构建日志能证明消费的是同一仓库、同一 digest 的镜像。

### BUILD-02：发布工作流没有限制 `workflow_run` 必须成功

- **确认事实**：`.github/workflows/docker-image.yml` 监听基础镜像工作流完成事件，但 release job 未检查 `github.event.workflow_run.conclusion == 'success'`。
- **影响**：基础镜像构建失败后，发布工作流仍可能继续执行并使用旧基础镜像或产生误导性发布结果。
- **处理方向**：增加成功条件，并区分 tag、手工触发和 workflow_run 三种上下文。
- **验收标准**：基础镜像任务失败时，发布任务明确跳过且不推送镜像。

### SEC-03：自动依赖维护和安全扫描基本关闭

- **确认事实**：`.github/dependabot.yml:7` 设置 `open-pull-requests-limit: 0`；未发现 CodeQL、依赖审计、容器扫描或 secret scanning 工作流。
- **影响**：已知漏洞不会自动形成升级入口，发布镜像也没有漏洞可见性。
- **处理方向**：恢复有上限的 Dependabot PR；增加 `pip-audit`、Maven/Node 审计、CodeQL、Trivy 或同类扫描。
- **验收标准**：引入已知高危依赖时 CI 失败，正常依赖更新会生成受控 PR。

### DEPLOY-01：应用容器默认以 root 运行，核心应用缺少健康检查

- **确认事实**：三个 Dockerfile 均未声明非 root `USER`；Compose 只为数据库和 Redis 配置健康检查，未发现 Python 服务和管理 Web/API 的应用级健康检查。
- **影响**：容器逃逸或文件写入风险扩大；编排系统只能知道进程存在，不能判断 OTA、WebSocket、控制 API 和管理 API 是否真的可用。
- **处理方向**：使用专用低权限用户；增加 HTTP/运行时 healthcheck；给服务设置合理的启动顺序和资源限制。
- **验收标准**：容器内 UID 非 0；关键接口失效时健康状态会失败并触发可观察的恢复动作。

### PRODUCT-01：真实设备验收仍有关键空白

- **确认事实**：`docs/operations/xiaoxin-real-device-acceptance-ledger.md` 将跨设备隔离标记为 `Pending`，部分 OTA、控制台、小程序和硬件项目仍为未验收或证据待归档。
- **影响**：自动测试证明不了 broker ACL、双设备隔离、固件订阅、真实 OTA、网络恢复和端到端隐私边界。
- **处理方向**：优先完成两台设备同时在线的跨设备隔离、真实 OTA、完整证据归档和回归台账。
- **验收标准**：每项结论包含设备、提交、delivery ID、日志/截图或视频，并能被第三方复核。

## 5. P2：近期架构与维护债务

### ARCH-01：核心文件体积过大

- **确认事实**：`core/xiaoxin/companion/store.py` 约 8602 行、`core/api/xiaoxin_control_handler.py` 约 3375 行、`core/connection.py` 约 2212 行；控制 handler 单类包含约 133 个函数。
- **影响**：代码审查难度、修改影响面、并发推理负担和合并冲突都会继续上升。
- **处理方向**：按照 schema/migration、Evidence、projection、worker queue、identity、delivery、HTTP resource 等稳定职责拆分，同时保持对外 interface 不变。
- **验收标准**：拆分由现有合同测试保护；外部调用方不需要了解内部子模块；不进行纯粹按文件行数切割。

### ARCH-02：文档已确认 legacy 与重复路径尚未清除

- **确认事实**：`docs/operations/current-handoff.md:65-70` 明确记录 Episode 重建、旧 JSON 迁移、重复实现删除等任务未完成。
- **影响**：新旧路径并存会放大状态不一致、双写、迁移和排障复杂度。
- **处理方向**：先定义单一事实源和切换门禁，再实现幂等迁移、dry-run、回滚和旧路径降级/删除。
- **验收标准**：运行时只有一个写入路径；旧格式只读兼容有明确期限；迁移可观察、可重试、可回滚。

### CODE-01：异常处理范围过宽，需要专项审计

- **确认事实**：自动扫描在 Python 文件中发现大量 `except Exception` 和若干 bare `except`。其中一部分可能属于 provider 边界或容错逻辑，不能仅凭数量判定错误。
- **影响**：宽泛捕获若没有结构化日志、状态转换和重抛策略，会隐藏真实故障并制造“服务还活着但功能已失效”的状态。
- **处理方向**：按网络边界、后台任务、数据库事务和纯业务逻辑分类审计；缩窄异常类型；禁止静默 `pass`；统一记录错误上下文和结果状态。
- **验收标准**：关键异常注入测试能证明事务回滚、用户可见错误、重试边界和日志均符合预期。

### DEVEX-01：缺少统一的一键验证入口

- **确认事实**：仓库未发现 Makefile、Taskfile、justfile 或统一验证脚本；Python、Java、Web、移动端使用各自命令。
- **影响**：开发者和 CI 容易运行不同的验证集合，“测试通过”缺少统一含义。
- **处理方向**：提供跨平台验证入口，至少包含快速检查、模块全量检查和发布前检查三个层级。
- **验收标准**：README、CI 和本地开发使用同一组底层命令，结果一致。

### DEPS-01：Python 依赖策略不一致且缺少锁定验证

- **确认事实**：大部分依赖精确固定，`powermem`、`paho-mqtt` 使用范围版本；没有 hash lock；`pyyaml==0.0.2` 版本需要在干净环境单独验证是否为预期发行物。
- **影响**：不同构建时间可能解析到不同依赖，或者在新环境安装失败；AI、音频和网络依赖的传递依赖尤其复杂。
- **处理方向**：区分人工维护的顶层依赖与机器生成的锁定文件；固定发布依赖并保存 hash；在 CI 做 clean install。
- **验收标准**：Linux amd64/arm64 和开发环境均能从锁文件完成安装，依赖树可追踪。

### DOC-01：当前交接快照已经落后于代码变化

- **确认事实**：`docs/operations/current-handoff.md` 更新时间为 2026-07-17，但仓库在 7 月 20-21 日继续大量合入语义记忆、主动陪伴、模型和语音工具变更。
- **影响**：新会话若把交接快照当成权威事实，可能基于过时任务状态做错误决策。
- **处理方向**：把交接快照改为自动包含当前提交和更新时间，或在每个能力合并时同步更新；把历史结论移入不可变台账。
- **验收标准**：交接文档引用当前主分支提交，能力状态与 requirements 和代码一致。

## 6. P3：长期升级成本

### FE-02：管理 Web 仍使用 Vue 2 和 Element UI 旧技术栈

- **确认事实**：管理 Web 使用 Vue `2.6.14`、Vuex 3、Element UI 2。
- **影响**：生态维护、现代工具链、安全修复和新人上手成本会持续恶化。
- **处理方向**：当前不要无目标重写；先建立测试和契约，再按页面或功能域渐进迁移。
- **验收标准**：迁移不改变后端合同，关键流程有自动化回归保护。

### CONFIG-01：已归档移动端曾跟踪环境专用地址

- **历史确认事实**：审计时的 `manager-mobile` 曾在环境文件中包含固定微信 AppID 和临时穿透地址；该移动端目录现已从仓库移除。
- **影响**：不同环境容易误连开发服务；临时隧道失效后默认构建行为不明确。
- **当前处理**：不再维护该移动端构建链；历史提交中的配置仍需按凭据轮换和历史清理流程单独处理。
- **验收标准**：当前生产路径不依赖该移动端目录。

## 7. 建议执行顺序

### 第一批：安全止血

1. 轮换高德 API Key。
2. 移除数据库、Redis 的工作型默认凭据。
3. 增加 secret scanning，并检查 Git 历史中的其他凭据。

### 第二批：建立可信交付

1. 补齐 Python 测试依赖和干净环境安装。
2. 打开 Java 测试。
3. 给 Web 增加 lockfile、lint、type-check 和基础测试。
4. 建立统一 CI，并阻止失败构建发布。
5. 修正基础镜像来源不一致。

### 第三批：完成真实闭环

1. 完成跨设备隔离与真实 OTA 验收。
2. 补齐可复核的日志、delivery ID、截图和视频。
3. 为 Python 服务和管理 API 增加健康检查与运行指标。

### 第四批：控制架构复杂度

1. 清除 legacy 双路径和未完成迁移。
2. 按稳定职责逐步拆分超大模块。
3. 审计异常处理和后台任务失败语义。
